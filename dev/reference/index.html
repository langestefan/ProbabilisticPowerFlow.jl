ProbabilisticPowerFlow.AbstractPFBackend — Type
AbstractPFBackend

A deterministic power flow solver backend. Interface definition:

  • init_state(backend, refs) -> state
  • set_injections!(state, backend, x)
  • solve!(state, backend; warmstart = nothing) -> SolveInfo
  • extract(state, backend, qoi) -> Float64

Optional:

  • supports_warmstart(backend) -> Bool, default false
  • linearize(backend, x0) -> (y0, S), which unlocks cumulant/PEM methods

See PowerModelsBackend for a fully usable example of the interface definition.

ProbabilisticPowerFlow.AdaptiveDesignPointSampling — Type
AdaptiveDesignPointSampling(event; n = 1000, rounds = 5, round_size = 200, defensive = 0.1,
    shift = nothing, proposal = nothing, fd_step = 0.1, maxiter = 20, tol = 1.0e-3)

Importance sampling for the probability of a rare ViolationEvent, with a proposal adapted to the violation region. Needs the ImportanceSamplers package.

It works in standard normal space like DesignPointSampling, in three stages:

  1. Find a design point z* for each finite bound lo and hi of event, with the same search as DesignPointSampling. An event with both bounds finite is violated below lo and above hi. These are two separate regions, so it gets two design points.
  2. Adapt a Gaussian proposal around each design point with AMIS from ImportanceSamplers.jl, in rounds rounds of round_size samples. A failed power flow counts as no violation.
  3. Draw n fresh samples from a mixture of the adapted proposals and N(z*, I), and weight them against that mixture. A share defensive of the samples comes from N(z*, I), which keeps the weights bounded where the adapted proposal is too narrow.

Only stage 3 gives the final valid estimate. AMIS reuses samples from earlier rounds, so its own estimate has no valid standard error. Fresh draws from the adapted proposal are IID, so the final estimate has a valid standard error.

The supplied event, or its quantity, must be one of the QoIs of the problem.

# both packages export IdentityTransform, so load only the module name
using ImportanceSamplers: ImportanceSamplers
over = ViolationEvent(VoltageMagnitude(5), -Inf, 1.1)
result = solve(prob, AdaptiveDesignPointSampling(over; n = 2000); rng = Xoshiro(1))
violation_probability(result, over), standard_error(result, over)

Stages 1 and 2 can be reused for new samples by calling solve(prob, result.method).

examples/adaptive_importance.jl compares this method with DesignPointSampling on a two-sided event.

ProbabilisticPowerFlow.Assignment — Type
Assignment(variable, target[, transform])

Describes how germ variables map to network components.

Germ variables have to be assigned to network components, optionally through an AbstractTransform. The transform is applied to the germ value before writing it to the component. Such a transform can for example be used when we specify windspeed as a germ variable, but use a power curve transform to get the generator's active power injection.

It is allowed to assign the same germ variable to multiple components, which expresses perfect correlation between those components. An example could be a constant powerfactor load.

ProbabilisticPowerFlow.DesignPointSampling — Type
DesignPointSampling(event; n = 1000, shift = nothing, fd_step = 0.1, maxiter = 20, tol = 1.0e-3)

Importance sampling for the probability of a rare ViolationEvent.

The method works in standard normal space. Every point z ∈ ℝ^d maps to the unit cube by u = Φ(z), and from there to physical injections through to_physical!. The marginals, the copula and the assignment transforms of the model are used as they are.

Instead of sampling z ~ N(0, I), samples are drawn from N(z*, I), centered on the design point z*: the most probable point at which the event just occurs. Each converged sample zᵢ gets the likelihood ratio

wᵢ = φ(zᵢ) / φ(zᵢ - z*) = exp(‖z*‖² / 2 - z*ᵀ zᵢ)

which violation_probability, mean and standard_error apply.

The design point is found with the improved HL-RF iteration on the limit state g(z) = min(y - lo, hi - y). Here:

  • y is the event's quantity
  • lo and hi are the event's bounds, and
  • g(z) < 0 means a violation occurred.

The gradient of g is a forward finite difference in z with step fd_step, which costs d + 1 power flows per iteration, plus one or more for the line search.

See design_point for details.

Pass shift to skip the search and center the samples on a user supplied point. Regardless, the estimate will be unbiased for any shift, because N(z*, I) covers all of ℝ^d. The shift only changes the variance.

A two-sided event, or an event that can be reached in separate regions of the input space, gets a shift toward the nearest region only, so the other regions are sampled poorly. Check standard_error and effective_sample_size to see how well the shift worked.

The supplied event, or its quantity, must be one of the QoIs of the problem.

over = ViolationEvent(VoltageMagnitude(5), -Inf, 1.1)
result = solve(prob, DesignPointSampling(over; n = 2000); rng = Xoshiro(1))
violation_probability(result, over), standard_error(result, over)

You can run solve(prob, result.method) to sample again with the same design point, without having to repeat the search.

ProbabilisticPowerFlow.GermVariable — Type
GermVariable(id, dist)

A named random variable of the germ, with marginal distribution dist, any UnivariateDistribution.

The germ is the set of all germ variables, and is the only source of uncertainty in a model. Everything else is derived from it, by a transform or by an assignment to a physical quantity. How germ variables are correlated is described by the copula in UncertaintyModel.

PPFProblem(backend, model, qois)

source
ProbabilisticPowerFlow.PPFResult — Type
PPFResult

The output of a sampling method. Fields:

  • method: the PPF method that was used.
  • qois: the estimated quantities of interest, in the row order of samples.
  • samples: n_qois × n_converged matrix of QoI values.
  • sample_indices: column j of samples came from sample sample_indices[j].
  • failures: the diverged samples, see FailedSample.
  • n_samples: the total number of samples taken.
  • n_solves: the total number of deterministic solves attempted, failures included.
  • weights: nothing for unweighted methods, otherwise the likelihood ratio of every converged sample, in the column order of samples. See DesignPointSampling.

Invariant: n_converged(r) + length(r.failures) == r.n_samples.

ProbabilisticPowerFlow.PowerModelsBackend — Type
PowerModelsBackend(data; alg = PowerModels.NativeNewton(), solver_kwargs = (;))
PowerModelsBackend(filename; alg = PowerModels.NativeNewton(), solver_kwargs = (;))

An AbstractPFBackend solving the AC power flow with PowerModels.jl.

data is a PowerModels network data dictionary in per unit, as returned by PowerModels.parse_file. It is validated and deep copied on construction, so mutating the dictionary afterwards does not change the backend. filename is a network file that PowerModels.parse_file can read, such as a MATPOWER .m file. alg is the solver algorithm handed to PowerModels._solve_nl, which defaults to a damped Newton method on the analytic sparse Jacobian.

Any NonlinearSolve.jl algorithm works once NonlinearSolve is loaded. Each state then keeps one solver cache and reuses its allocations and symbolic factorization for every solve, so a sparse factorization such as NewtonRaphson(linsolve = KLUFactorization(check_pattern = false)) pays off.

solver_kwargs is a NamedTuple of keywords passed on to the solver, such as (abstol = 1.0e-10, maxiters = 20) for a NonlinearSolve algorithm. NativeNewton takes no keywords and is configured through its own constructor.

Only quantities Pd and Qd on loads and Pg on generators can be assigned. Anything else is rejected by init_state. This includes Qd at a PV bus, and any assignment at the slack bus.

using ProbabilisticPowerFlow, PowerModels

backend = PowerModelsBackend("case5.m")
state = init_state(backend, [ComponentRef(ComponentField.Pd, 1)])
set_injections!(state, backend, [0.5])
info = solve!(state, backend)
extract(state, backend, VoltageMagnitude(3))

ProbabilisticPowerFlow.SolveInfo — Type
SolveInfo(converged, iterations, residual)

This stores the outcome of a single deterministic power flow solve.

converged is true if the solver reached the specified tolerance, iterations is the number of iterations taken by the solver, and residual is the final infinity-norm of the power mismatch.

Backends must return this from solve! and must never throw when a solve diverges, leaving the state usable for the next solve.

A backend that converges must report a real residual. Only a diverged solve may use SolveInfo(false, -1, Inf), for a solver that reports neither the iteration count nor the final residual.

ProbabilisticPowerFlow.UncertaintyModel — Type
UncertaintyModel(variables, assignments, dependence)
UncertaintyModel(variables, assignments)

The full description of the uncertainty in a model: the germ variables, their mapping onto network components through assignments, and the dependence structure between the germ variables.

The dependence structure is a copula, a multivariate distribution with uniform marginals. Its dimension must equal the number of germ variables, because the two together are one joint distribution. The two-argument form defaults to an IndependentCopula of the right dimension.

Internally we cache varindex, a static mapping from assignment order to germ variable order, so to_physical! reads an integer index instead of resolving a name once per assignment per sample.

Validated on construction: germ variable ids are unique, every assignment references a declared germ variable, every germ variable is referenced by at least one assignment, and the dependence dimension matches. Component existence in the network is the backend's half, enforced by init_state.

ProbabilisticPowerFlow.ViolationEvent — Type
ViolationEvent(qoi, lo, hi)

Indicator QoI: 1.0 when qoi falls outside [lo, hi], 0.0 otherwise.

It is defined as a QoI rather than retrieved through post processing, so that rare-event methods such as importance sampling and subset simulation can dispatch on it and target the specific event they're looking for. The Monte Carlo mean is the violation probability of the event.

solve(prob::PPFProblem, method::AbstractPPFMethod; rng, warmstart = :off, scheduler)

Estimate the QoIs of prob with method. One call runs many deterministic solve! calls on the backend.

  • warmstart: :off starts every solve cold, :chain from the previous solution, and :sorted does the same after sorting the samples by total injection.

ProbabilisticPowerFlow.design_point — Method
design_point(prob, event; fd_step = 0.1, maxiter = 20, tol = 1.0e-3) -> (z*, n_solves)

Search for the most probable point of the limit state surface g(z) = 0 of event with the improved HL-RF method (Zhang and Der Kiureghian, 1995). The gradient is a forward finite difference with step fd_step.

Each iteration linearizes g at z and finds the point of the linearized surface that is closest to the origin:

z̃ = (∇gᵀ z - g(z)) / ‖∇g‖² · ∇g

Plain HL-RF jumps to z̃ and can oscillate when g is strongly curved, as it is with light-tailed marginals or an asymmetric copula. Here the step z → z̃ is halved until the merit function ½‖z‖² + c |g(z)| decreases, with c = 2 max(‖z‖, ‖z̃‖) / ‖∇g‖, and also while the power flow diverges, at most 10 times. The search has converged when the full step ‖z̃ - z‖ is below tol · max(1, ‖z‖).

ProbabilisticPowerFlow.effective_sample_size — Method
effective_sample_size(r::PPFResult, v::ViolationEvent)

Effective number of violating samples, (Σ wᵢ)² / Σ wᵢ² with the sums over the converged samples that violate v. For an unweighted result this is the number of violations.

This is what sets the precision of violation_probability. With importance sampling a value far below the number of violating samples means a few of them dominate the estimate, so the shift missed part of the violation region. As a rule of thumb, an estimate based on fewer than about 30 effective samples is not reliable.

ProbabilisticPowerFlow.solve_blocks — Method
solve_blocks(f, scheduler, order) -> Vector{FailedSample}

Solve the samples in order by dividing into separate blocks.

order holds the sample indices. A block is a single slice of it. f solves one block and returns the samples that failed. Every block gets its own state tracked by the backend, so that warm starts are only re-used within the same block. The scheduler decides how to run the blocks. If scheduler is nothing, the blocks are run serially in the current task.

Without a scheduler there is one block. Load OhMyThreads.jl to run the blocks on separate tasks.
